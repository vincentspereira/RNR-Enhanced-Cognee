## Recommended decision

Use a thin native Hermes memory provider calling a restricted Enhanced Cognee
service. Keep Hermes' built-in notebook. Start with a dedicated synthetic profile
and an isolated data store. Admit cross-project sharing only after storage and
identity isolation pass real-stack tests.

Do not attach Hermes directly to all 122 existing tools. Do not install an
upstream Cognee engine over the fork, mount the Workspace checkout into Hermes,
or assume a dataset name is an authorization boundary.

The existing upstream Cognee plugin remains a reuse option if a contract test
proves that its standard REST calls reach the intended Enhanced stores under
equivalent authorization. The retained upstream API in cognee/api/client.py has
the expected route names, but separate configuration/schema paths; matching names
are insufficient. The current upstream integration's pyproject pins upstream
Cognee while this fork declares 1.0.9+enhanced. Do not force an in-process package
swap to satisfy that pin. A thin HTTP-only connector avoids that coupling.

## Target architecture

Hermes runs in isolated Ubuntu-Hermes. It cannot access Windows or
Ubuntu-Workspace files. It must obtain the integration from GitHub into its own
checkout. The recommended first test places a dedicated memory service inside
Ubuntu-Hermes and uses invented data. It does not require opening access to the
other environments. The diagram shows the later shared-service option; that
option requires a separately approved private network connection. Neither
placement makes memory private from an agent that also has administrator access
to the service's files or database; that boundary must be checked before real use.

```text
Ubuntu-Hermes
  Hermes profile
    MEMORY.md / USER.md: small working rules and preferences
    enhanced_cognee provider: recall, explicit remember, controlled capture
         |
         | restricted authenticated API; no direct DB or filesystem access
         v
Memory service outside Hermes
  Verified actor + tenant/project policy
  Admission, provenance, versioning, idempotency, content limits
  One MemoryService + RecallService used by every transport/dashboard
         |
         +-- PostgreSQL: canonical versioned records and outbox
         +-- Qdrant: derived embeddings with matching actor scope
         +-- ArcadeDB: derived entities/relationships with matching scope
         +-- Valkey: bounded disposable cache with matching scope
```

Separate deployments, keys, and storage should remain available for domains whose
confidentiality differs substantially, particularly family or regulated records.
The goal is reusable memory infrastructure, not universal visibility of private data.

## Phase 2 - Make storage and memory semantics consistent (F04-F09, F16, F18, F20, F25)

Proposed new core modules, with final names chosen during implementation:

- `src/memory_service.py`: remember/get/update/retract/list; authenticated actor
  scope, provenance, versions, idempotency, and admission policy.
- `src/recall_service.py`: text/vector/graph retrieval with the same authorization
  constraints and explicit indexing readiness.
- `src/memory_contracts.py`: typed requests/results, status/error codes, and scope.
- `src/index_outbox.py`: durable work derived atomically from canonical writes.
- A shared scoped repository interface for storage providers rather than copying
  SQL into transports and relying on callers to remember a context manager.

Existing HTTP, stdio, dashboard, integration helpers, provenance/versioning,
encryption, and erasure code should delegate to those modules. Preserve old
interfaces through tested adapters while migrating; avoid a wholesale rewrite.

Required record fields:

| Field group                                          | Purpose                                               |
| ---------------------------------------------------- | ----------------------------------------------------- |
| Immutable ID, version, idempotency key               | Stable corrections and retry safety                   |
| Tenant, project, owner subject, writer agent         | Enforce ownership and sharing                         |
| Session/source ID, source URI/hash/span              | Make recalled claims traceable                        |
| Created/observed/verified dates and expiry           | Identify stale or superseded facts                    |
| Fact, preference, decision, inference classification | Separate evidence from agent conclusions              |
| Trust/authority/confidence and correction lineage    | Preserve conflicts without silently rewriting history |
| Admission and indexing status                        | Distinguish accepted text from graph/vector readiness |

Categories remain configured strings; no fixed ATS/OMA/SMC enumeration.

Choose one migration authority and reconcile UUID/TEXT IDs, JSONB encoding,
missing columns, and tenant-related constraints. Generate and query embeddings
with one explicit model/version/dimension contract. A plain text search does not
qualify as semantic or multi-hop graph recall.

When application encryption is required, define where decryption is permitted
for indexing and retrieval. Require persistent keys, key IDs, restore/rotation
tests, and fail-closed protected writes. Explain residual derived-data exposure.

Acceptance: new-install and upgrade fixtures, matching storage scopes, paraphrase
recall, source-grounded multi-hop answers, correction/forget across derived stores,
restart and partial-failure recovery. Irreversible cleanup requires a separate
owner-approved retention/deletion decision.

## Phase 4 - Native Hermes provider

Proposed location inside this repository:

```text
integrations/hermes/enhanced_cognee/
  __init__.py       MemoryProvider implementation and register entrypoint
  plugin.yaml       Provider identity and dependency metadata
  pyproject.toml    Thin client dependencies; no upstream cognee engine pin
  client.py         Restricted API client with identity/error/timeout handling
  config_schema.py Profile-specific non-secret configuration
  README.md        Installation, data policy, troubleshooting, rollback
  tests/           Contract, lifecycle, isolation, and failure tests
```

Hermes' documented directory installation is `$HERMES_HOME/plugins/<name>/`.
Use its supported dependency preparation for the pinned Hermes version. Do not
modify Hermes core or inject a replacement Cognee package into its environment.

Map the documented lifecycle to the service:

| Hermes lifecycle                    | Proposed behavior                                                                                                 |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| is_available / initialize           | Validate profile config without hidden network/model startup; connect with a restricted identity                  |
| system_prompt_block                 | Explain source trust, current capability, and available memory actions                                            |
| prefetch                            | Relevant scoped recall with a small configurable context/time budget                                              |
| sync_turn                           | Non-blocking durable admission of allowed summaries/facts, with retry identity                                    |
| on_memory_write                     | Mirror permitted notebook additions/corrections using exact identity; do not guess deletes on older hook metadata |
| on_session_end / shutdown           | Flush acknowledged work and expose pending/failing indexing                                                       |
| get_tool_schemas / handle_tool_call | A small set of scoped remember/recall/correct/status actions                                                      |

The owner selected automatic capture of useful decisions, preferences and task
summaries for the synthetic profile. Hermes' main model selects synchronous tool
writes; raw transcript and notebook mirroring hooks remain disabled. The original
explicit-only recommendation has been superseded. Do not archive every tool
output, private chat, credential or personal document.

Suggested initial recall budget: top 5 results and approximately 1,500-2,500
tokens, adjusted after real retrieval evaluation. These are design starting
points, not measured optimal values or promises about accuracy.

Do not expose backup/restore, arbitrary file/database ingestion, raw Cypher,
notification sends, administrative consent operations, or all 122 tools to Hermes.

Use fake names and project facts in two disposable Hermes profiles.

2. Retrieve by paraphrase, then ask a question requiring two linked facts.
   Inspect returned provenance; do not accept a plausible unsupported answer.
3. Show that built-in notebook contents are not the explanation by using a
   disposable fresh profile, without clearing Vincent's real notebook.
4. Correct a fact and verify the old version no longer wins normal recall.
5. Test scope separation, forbidden actions, expiry, and prompt-injection content.
6. Interrupt the service during a write/session close; verify recovery, one logical
   record per idempotency key, and a clear unavailable/degraded status.
7. Restart service and Hermes; repeat recall and protected-content checks.
8. Restore a disposable backup and prove data, keys, indexes, and permissions.
9. Measure retrieval quality, latency, model calls, storage growth, and local

   assume that self-hosted databases prevent external model calls.

permission/isolation results, retrieval scores, and a restore record.
